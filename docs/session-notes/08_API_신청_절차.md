## 데이터 파이프라인 개념 정리 (Q&A 시리즈)

**"청킹 필요한가?"** → 필요 없음. NCS `compeUnitDef` 최대 1000자, 채용공고 `jobCont` 몇백 자, 훈련과정명 한 줄 — 전부 Upstage 권장 512토큰 이내. 흐름: 필드 결합(레이블링 방식 권장) → 레코드 1건=임베딩 1건 → `job_postings.embedding`에 저장.

**"지저분하게 나오지 않을까?"** → 지저분함은 임베딩 자체가 아니라 ①결합 방식(레이블 없는 순수 concat) ②LLM 프롬프트 전달 형태(구조화 안 된 blob)에서 생김. 대응: 레이블링 결합 + 검색 결과를 구조화된 형태로 LLM에 전달 + 유사도 임계값·top-k 필터링.

**"1024차원과 청킹 안 하는 이유가 같은 건가?"** → 별개. 청킹 미사용은 텍스트가 짧아서(텍스트 길이의 결과), 1024차원은 `solar-embedding-2` 모델 스펙 자체(모델 선택의 결과) — 인과관계로 묶으면 안 됨.

**"업스테이지 임베딩 차원수를 친구가 왜 물어봤을까?"** → pgvector 컬럼(`Vector(EMBEDDING_DIM)`) 정의에 그대로 들어가야 하는 값이라, DB/적재 코드 작성 중이면 필수로 확인해야 하는 값이라는 설명.

**BGE-M3 vs Upstage Solar Embedding 2 비교표** — 둘 다 1024차원, 성능 비슷. 해커톤 맥락에서는 Upstage가 명확히 유리(호스팅 API라 인프라 불필요, 이미 통합·테스트 완료). BGE-M3는 API 비용 부담 시 대안으로 남겨둠.

**"스파스를 못 잡는다는 게 무슨 뜻?"** → 정확한 키워드/용어 일치를 놓친다는 뜻. 덴스(Upstage)는 의미 유사도는 잘 잡지만 "SQL" 같은 정확한 문자열 매칭엔 약함. BGE-M3는 덴스+스파스+ColBERT 하이브리드가 특징. 자격증명·기술 스택명 정확 매칭이 중요한 JobExplorer엔 이론상 영향 있으나 MVP 규모에선 덴스만으로 충분, 필요시 키워드 필터+벡터 유사도 하이브리드로 보완 가능.

## 전체 파이프라인 순서 재정리

**사용자**: 우리 프로젝트가 이력서 및 자유 형식의 경력을 입력하면 코사인 유사도를 통해 역량 키워드를 뽑아주는거야?

**어시스턴트**: 아니요, 반대 순서. 역량 추출은 **LLM**이, 코사인 유사도는 그 다음 매칭 단계에서만 사용.

**최종 정리 (STEP별)**:
- **STEP 1 Diagnosis**: 경력 텍스트 → LLM이 자동화 위험도 진단(KEIS 대체율 데이터 결합) → 위험도 점수+근거
- **STEP 2 SkillProfile**: 같은 텍스트 → LLM이 전이 가능한 역량 단위로 분해(코사인 유사도 없음, 전부 LLM) → 역량 리스트, 사용자가 직접 검토·수정
- **STEP 3 JobExplorer**: 확정된 역량 프로필을 Upstage query 모델로 임베딩 → 사전 적재된 채용공고/NCS(passage 모델) 벡터와 **pgvector 코사인 유사도** 비교(코사인 유사도가 쓰이는 유일한 지점) → 인접 직무 랭킹
- **STEP 4 Roadmap**: 목표 직무-현재 역량 격차를 LLM이 분석 → HRD-Net 훈련과정 매칭(RAG)

LLM이 두 번(역량 분해, 격차 분석), 코사인 유사도는 STEP 3 딱 한 번만 사용되는 구조.

## 정규화·통합 개념 Q&A

**"필요한 데이터만 받아와도 통합은 필요한거지?"** → 필요함. "선택적 호출"은 *양*의 문제, "통합(정규화)"은 *구조*의 문제 — 서로 다른 문제.

**"원본 필드를 왜 통합해?"** → 4가지 이유: ①필드명이 소스마다 달라 매번 분기 처리 필요 ②임베딩·유사도 검색은 통일된 텍스트 필드가 있어야 작동 ③소스 추가 시 확장성(변환 함수 하나만 추가) ④근거(evidence) 표시 일관성(CLAUDE.md 원칙).

**"손봤냐는 질문의 의미"** → "임베딩 전에 데이터를 정리(정규화)했냐"는 뜻. 당시 상태로는 정규화 함수는 설계만 되고 구현은 안 된 상태였음.
