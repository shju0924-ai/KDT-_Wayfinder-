# Wayfinder — "투 트랙 알고리즘" 세션 (2026-08-07)

두 갈래 트랙(인접 직무 전환형 / 교육 후 직무 전환형) 설계와 실제 구현 간 격차를 진단하고, 콜센터 상담원 페르소나로 실측하며 알고리즘을 여러 차례 수정한 세션. 세션 중반부터 model을 opus로 전환해 대규모 재설계 진행.

---

**사용자**: 우리가 구상한 지금 두 갈래의 트랙인데 지금 코드로는 얼마나 구현 할 수 있을까?

**어시스턴트**: 그림의 5개 행을 축으로 코드 대조.

| 그림의 행 | 현재 코드 | 구현률 |
|---|---|---|
| 사용자 선택 (2갈래) | [JobPathChooser.tsx](frontend/src/components/cards/JobPathChooser.tsx) 2버튼 → `search_track` 쿼리 파라미터 | 거의 완성 |
| 검색 범위 (현 직무군 중심 vs 확장) | 두 트랙이 같은 SQL·같은 전체 테이블 검색 | 40% |
| 정렬 기준 (유사도 vs LLM 재비교) | 벡터 1차 정렬 + LLM 선별, 사후 격차 필터 | 50% |
| 후보 예시 | 수집 DB에 실제 존재해야 함(미검증) | 데이터 의존 |
| 결과 (짧은 보완 vs 중장기 확장 로드맵) | STEP 4로 전달조차 안 됨 | 0% |

핵심 문제: [embedding.py:65](backend/app/services/embedding.py:65)의 `_JOB_SEARCH_SQL`이 트랙 무관하게 전체를 훑고, "직무군" 개념 자체가 스키마에 없음. 현 직무 배제는 제목 문자열 부분일치가 전부라 이름이 다른 같은 직무군은 못 거름. 우선순위: ①로드맵 트랙 분기 → ②적합도 표기 이원화 → ③NCS 분류 매핑(무거워서 MVP 이후 권장).

---

**사용자**: 이미지에 있는 방식이 구현 가능한 부분이야?

**어시스턴트**: 새 인프라·모델 불필요, 전부 구현 가능. "바로 가능"(문구 교체·정렬 이원화·선호 반영·로드맵 분기, 합쳐서 2~3일)과 "조건부 가능"(검색 범위 확장 — NCS 분류 매핑 or `training_courses`에서 출발하는 소스 전환)으로 구분. 진짜 리스크는 새 직무 트랙이 빈 결과로 떨어지는 것 → DB 실측이 먼저.

---

**사용자**: 콜센터 상담원→인접 직무 외 추천→공사현장 품질팀. 품질 관리에 대한 역량을 공사현장으로 인식하여 너무 거리가 먼 걸 추천해준게 아닌가

**어시스턴트**: 데이터 문제가 아니라 코드가 만든 실패. 세 원인 중첩:
1. [jobs.py:77](backend/app/api/routes/jobs.py:77)에서 역량 이름만 쓰고 evidence·category 버림 — 맥락 없이 임베딩.
2. 새 직무 트랙 검색 문맥이 "인접 직무는 제외"라 상담 도메인에서 **멀어질수록 가산점**.
3. 거리 상한이 아예 없음 — gap_ratio 하한만 있고 상한 없어서, 요구역량을 하나도 못 채우는 직무가 최적해.

수정안: A) 하한·상한 도입, B) 선별 프롬프트 기준 교체, C) 맥락 실어 임베딩(반나절). A·B 즉시 적용 요청받아 진행.

---

**사용자**: 우리가 생각한 유사 직무는 쇼호스트, 영업사원과 같은 말을 많이 하는 직군을 나오게 하고 싶었거든

**어시스턴트**: C번(맥락 실어 임베딩) 적용. [embedding.py](backend/app/services/embedding.py), [jobs.py](backend/app/api/routes/jobs.py), [llm.py](backend/app/services/llm.py) 3개 파일 수정 — `_skill_search_text()` 추가(역량명+카테고리+근거 문장 결합), `_matches_track()`이 교육 트랙에 상한(0.75)+최소 연결 역량 1개 추가, 선별 프롬프트에 "같은 단어를 다른 산업 맥락에서 쓰는 경우 이어지는 것으로 보지 말라" 명시.

---

**사용자**: (도커 기동 후) 완료된 거 같아

**어시스턴트**: 실제 DB로 콜센터 페르소나 검증 스크립트 실행. 결과: 교육 후 전환형은 개선됐으나(`[Tibero] 품질관리 담당자(QA)` 등 합리적 매칭), **인접 직무 전환형은 5건 전부 탈락** — 별개의 기존 버그. LLM이 뽑는 `required_skills`가 세부 항목까지 포함되며 gap 비율이 항상 0.4를 넘어버림. A(임계값 완화 0.4→0.6)와 B(상대 기준 전환) 중 A를 제안.

---

**사용자**: 페르소나는 우선 콜센터 상담원 하나로만 쭉 밀고 나갈 예정이야

**어시스턴트**: 3회 실측: 0.4는 2/3 0건, 0.5도 2/3 0건, 0.6은 3/3 안정. 0.6으로 적용, 교육 트랙 상한도 재조정(0.6~0.85) 후 재검증 — 교육 트랙 3/3 안정, 인접 트랙은 2/3만 결과 있음(LLM 선별 변동성이 원인, 임계값 문제 아님).

---

**사용자**: 전환 후보에 대학 행정 조교 같은 부분은 전문성이 있는 직업이 아니라 꼭 교육 로드맵을 듣고 이직을 해야하나?

**어시스턴트**: 지난 임계값 확대(0.85)가 만든 부작용. `missing_skills`가 역량 격차가 아니라 회사 내부 운영 절차("학습자 출결 체크" 등)를 뽑고 있었음 — 훈련과정으로 못 채울 항목. `_JOB_JUDGE_SYSTEM`([llm.py:254](backend/app/services/llm.py:254))에 "훈련 가능성" 필터 추가 → missing_skills 문구가 "교육과정 기획·운영" 등 더 큰 단위로 개선됨. 다만 "대학 행정조교"는 3/3 계속 등장 — 이건 프롬프트가 아니라 데이터 한계(전문직 공고 자체가 적음)로 판단.

---

**사용자**: 우리는 필요한 역량이 비슷하면 개발자와 같은 부트캠프를 이용해서 새로운 직무를 추천해주는 느낌인데 계속 사무직 관련으로만 나와서

**어시스턴트**: 구조적 한계 진단 — 교육 트랙도 "역량 벡터로 공고 검색" 방식이라, 개발자 공고 요구역량(Python·Git)이 상담 역량 벡터와 임베딩 공간에서 멀어 애초에 후보에 못 낌. **검색 방향을 뒤집는 재설계 필요**: 역량 밑바탕 → LLM이 새 직무 제안 → 훈련과정 존재 확인(하드 게이트) → 실채용 확인.

`/model claude-opus-4-8` 전환 후 "진행해" 승인받아 TaskCreate로 작업 추적하며 구현:
1. 임계값 실측(훈련과정 존재 판정 0.55로 결정 — 부트캠프 대상 직무는 0.57~0.65, 대조군은 0.46)
2. `suggest_training_targets()` LLM 함수 신설 ([llm.py](backend/app/services/llm.py))
3. `jobs.py`를 인접/교육 두 분기로 분리, 교육 트랙은 역전 파이프라인
4. [JobMatchList.tsx](frontend/src/components/cards/JobMatchList.tsx) 라벨 트랙별 분기("적합도" vs "전이 가능성")

결과: 데이터 분석가·디지털 마케터·소프트웨어 테스터·UX 리서처·RPA 개발자·웹 개발자 등장, 근거(evidence) 인용 포함. 인접 트랙은 손대지 않음.

한계 — 3회 중 1회는 여전히 빈 결과, `requirement_excerpt`의 전이 근거가 화면에 미노출.

---

**사용자**: 무조건 개발자 직무를 추천하라는 것은 아니야 알지?

**어시스턴트**: 실측에서도 디지털 마케터·UX 리서처·CRM 마케터 등 비개발 직무가 더 많이 나왔음을 확인. 다만 `_TRAINING_TARGET_SYSTEM` 프롬프트의 예시가 IT 위주라 앵커링 우려 있음 — 편향 제거(A) vs 다양성 보장(B) 중 어느 쪽이 걱정되는지 질문. (결론 미확정 상태로 세션 계속)

---

**사용자**: (model을 sonnet-5로 복귀) 전이 가능성이라고 나오는 수치는 뭐야?

**어시스턴트**: `_match_training_transition`의 계산: `fit = len(transferable) / len(required) * 100`. 인접 트랙의 코사인 유사도 기반 fit_score와 계산 원리가 완전히 다른데 화면엔 같은 방식(숫자+막대)으로 노출됨 — LLM이 뽑은 두 리스트 개수 비율일 뿐, 항목 "무게"를 반영하지 않고 시도마다 값이 흔들림. 개선안 두 가지 제시.
